# 不會當場炸的越界:zone 上界失守與隨機當機

引擎畫一張圖時,用「圖號 ÷ 100」算出這張圖存在哪個資源檔(zone)。圖號來自遊戲腳本、型別是 16 位元,最大 65535 —— 除以 100 之後 zone 可以到 **655**。但存放 zone 的陣列只有 **450** 個項目,而且上游的程式碼是**先取陣列元素、才做邊界檢查**,所以那次讀取擋不住。

這顆的關鍵特性是**它不會當場崩潰**。索引 650 越過陣列尾端 9600 bytes,但那個位置仍然落在 `AGOSEngine` 物件內部,讀到的是其他成員變數 —— 拿到一個看起來合法的指標,程式繼續跑,然後在**完全無關的地方**倒下。「玩一陣子當機、每次當的地方都不一樣、找不到規律」就是這種 bug 的形狀。

修法是在碰陣列之前先擋上界,而上界照這款遊戲的實際用量訂:靜態盤點與遊戲檔都指向最高 zone 74,取 74 × 1.1 = 82。

**這顆不是玩家回報的,也沒有從玩家端證實過。** 它是在討論「要不要把陣列開大」時,為了回答那個問題去逐一盤點所有索引點才發現的。下面會說明為什麼不能宣稱它就是玩家遇到的那顆。

---

## 前提

1. 圖號的型別是 `uint16`,所以 `zoneNum` 的理論上界是 655。依據是 `setImage(uint16 vgaSpriteId, …)` 與 `animate(…, uint16 vgaSpriteId, …)` 的簽名。
2. `VgaPointersEntry` 在 64 位元平台上是 48 bytes(6 個指標)。位移的計算建立在這個尺寸上;32 位元平台會是 24 bytes,越界的距離不同但性質相同。
3. Elvira 1 的最高 zone 是 74。依據是靜態盤點與遊戲檔清單兩邊都指向 74,兩者一致。
4. 「垃圾值只從 `setImage()` / `animate()` 進來」這個結論,建立在對 25 個索引點的來源追溯上;追溯用的是靜態閱讀,不是執行期追蹤。

## 怎麼發現的

起點是一個質疑:既然陣列只有 450 而 zone 可能更大,**那不是應該把陣列加大、留安全邊際嗎?**

要回答這個問題,得先知道有多少地方會索引那個陣列、值分別從哪來。全部盤出來是 25 處:

| 索引點 | zone 值的來源 | 有沒有保護 |
|---|---|---|
| `setImage()` / `animate()` | 腳本圖號 ÷ 100 —— **唯一會進來垃圾值的入口** | 原本沒有 |
| `draw.cpp` 六處 | `vsp->zoneNum`,由 `animate()` 寫入 sprite | 上游已驗證過才寫進去 |
| `event.cpp` | VGA 事件佇列,由 `animate()` 排入 | 同上 |
| `zones.cpp` `checkNoOverWrite()` | `_noOverWrite` | **上游自己擋了**:`if (_noOverWrite == 0xFFFF) return;` |
| `charset` / `icons` / `res` / `script_e1` | 寫死的常數(1、2、7、8、11) | 不需要 |
| `cursor.cpp` 一處 | Puzzle Pack 專用,不走 Elvira 路徑 | 不適用 |

盤完之後兩件事同時清楚了:**垃圾值只有兩個入口**(所以檢查放在那兩處就夠),以及**那兩個入口原本沒有上界檢查**(所以這是個真的洞)。

順帶也回答了原本的問題 —— 見下面〈為什麼不是把陣列開大〉。

## 根因

`setImage()` 與 `animate()` 的主迴圈長這樣:

```cpp
zoneNum = vgaSpriteId / 100;

for (;;) {
    vpe = &_vgaBufferPointers[zoneNum];   // ← 越界讀發生在這裡
    if (vpe->vgaFile1 != nullptr) break;
    loadZone(zoneNum);                    // ← CHECK_BOUNDS 在這之後才執行
}
```

`loadZone()` 開頭確實有 `CHECK_BOUNDS(zoneNum, _vgaBufferPointers)`,但那是**斷言,而且在讀取之後**。取 `&_vgaBufferPointers[zoneNum]` 這一步先發生,斷言擋不到它。

### 為什麼不會當場炸

```
每個項目          48 bytes(6 個指標)
陣列              450 × 48 = 21600 bytes
索引 650 的位移   650 × 48 = 31200 bytes
越過陣列尾端      31200 − 21600 = 9600 bytes
```

`_vgaBufferPointers` 是 `AGOSEngine` 的成員,而 `AGOSEngine` 物件遠大於 9600 bytes。所以越界的那 9600 bytes **仍然落在同一塊配置內部**,讀到的是其他成員變數的內容 —— 一段完全合法、已映射的記憶體。

於是 `vpe->vgaFile1` 拿到的是某個成員變數的位元組被當成指標解讀的結果。它可能是 null(迴圈繼續、呼叫 `loadZone` 觸發斷言),也可能是一個非 null 的垃圾指標 —— 那就直接 `break` 出迴圈,後面拿它去讀圖檔內容,在**離出事點很遠的地方**崩潰。

這解釋了三件玩家層面的觀察:當機時機隨機、當機位置每次不同、以及在不同機器上重現率差很多(取決於物件記憶體佈局與那幾個成員當下的值)。

### 為什麼 ASan 抓不到

AddressSanitizer 的邊界檢查靠 **redzone** —— 在每塊配置的前後夾一段毒化區域。它保護的是**配置與配置之間**的邊界。

而這是**同一塊配置內部**的越界:物件成員陣列越界到別的成員。中間沒有 redzone 可言,對 ASan 來說那就是一次合法的記憶體存取。

實際情況:這顆被發現之前,已經跑過五輪 ASan 掃描(x2、x3 非整數倍、x4 高倍率、OpenGL、比例校正),**全部乾淨**。它是逐行讀程式碼才浮出來的。

> 這是「ASan 乾淨不等於程式正確」最具體的一個例子。工具的能力邊界要當成已知條件納入測試計畫,而不是用完就當作驗過了。

## 修法

在碰陣列之前擋上界,`setImage()` 與 `animate()` 各一份:

```cpp
static const uint kChtElvira1ZoneLimit = 82;   // 74 x 1.1

const uint chtZoneLimit = (getGameType() == GType_ELVIRA1)
        ? kChtElvira1ZoneLimit : (uint)ARRAYSIZE(_vgaBufferPointers);
if (zoneNum >= chtZoneLimit) {
    warning("%s: zone %d 超出上界 %u(sprite id %d), 跳過此圖",
            __FUNCTION__, zoneNum, chtZoneLimit, vgaSpriteId);
    return;
}
```

其他 subengine 不套 Elvira 的數字,沿用陣列大小(zone 需求最高的是 Feeble Files 的 450)。

### 上界怎麼訂

82 是量出來的:

| 來源 | 最大值 | 對應 zone | 驗證方法 |
|---|---|---|---|
| GAMEPC 子程式的 `PICTURE` 常數 | 7403 | **74** | Test(全 TABLES dump) |
| `ANIMATE` 常數 | 7201 | 72 | Test |
| VGA 腳本的 `SET_WINDOW_IMAGE` | 6602 | 66 | Test(全 zone dump) |
| 以變數當圖號者,變數的最大指派值 | 5632 | 56 | Test |
| 遊戲檔實際存在的最高 zone | — | **74**(`741.vga` / `742.vga`) | Test(盤點檔案) |
| 執行期實測(220 次隨機操作走到的最高) | 6903 | 69 | Test(插樁量測) |

靜態上界(74)與檔案上界(74)一致,取 74 × 1.1 = 81.4,進位 **82**。

**[HARD] 不能用 `_numZone` 當上界。** Elvira 1 的 `_numZone` 是 74,而 zone 74 **確實會用到** —— 照慣例寫 `zoneNum >= _numZone` 會把合法內容擋掉。看起來更嚴謹的檢查反而誤擋,這種地方寧可保守。

### 為什麼不是把陣列開大

「加大陣列、留安全邊際」是很自然的直覺,但在這裡行不通,三個層次:

**做不到。** 這套程式碼有些地方用 `0xFFFF` 當「無效」的哨兵值(例如 `_noOverWrite`)。要靠尺寸覆蓋到那個,陣列得開 65536 個項目 —— 乘上每項 48 bytes 是 **3 MB**。而且 `0xFFFF` 根本不是「第 65535 個 zone」,它是「沒有」。**分辨語意的事情不能靠容量解決。**

**沒有必要。** 垃圾值只有兩個入口,檢查放在那兩處就完整覆蓋;其餘 23 處索引消費的都是已經驗證過的值。加大陣列不會多保護到任何一處。

**有代價。** `450` 是 Feeble Files 的 `_numZone`。動它等於改 `AGOSEngine` 的物件佈局,影響所有 subengine,patch 侵入性與跨 ScummVM 版本重對的成本都變大。

記憶體成本反而不是考量 —— 450 → 656 只多約 10 KB。所以這不是「省記憶體 vs 防崩潰」的取捨,而是**用容量去容納不合法的值,方向本身就錯了**。

## 驗證

| 項目 | 結果 | 驗證方法 |
|---|---|---|
| 圖號 7403 → zone 74(合法最高) | 放行,且 `loadZone(74)` 實際載入成功 | Test |
| 圖號 8200 → zone 82(剛好到上界) | 拒絕 | Test |
| 圖號 65000 → zone 650(遠超陣列) | 拒絕,不再有越界讀 | Test |
| 圖號 99 → zone 0(不存在的 zone) | 上界放行,由第二道「檔案不存在」防護擋下 | Test |
| 正常遊玩會不會誤擋 | 200 次操作,誤擋 0 次、缺檔跳過 0 次 | Test |
| 出貨包壓力測試 | 兩種顯示後端各 350 次密集操作,無崩潰、log 無錯誤 | Test |
| ASan 迴歸 | x3 / x4 / OpenGL / 比例校正四輪全乾淨 | Test |
| patch 可從乾淨的 v2.9.1 樹套用並編譯 | 通過 | Test(macOS CI) |

第一列是這次驗證裡最重要的一項。上界訂太緊會誤擋合法內容,而誤擋的症狀是「某個畫面莫名其妙不見了」,比崩潰更難查。

### 一個測試方法的坑

第一次想驗證時,直接在引擎初始化階段呼叫 `setImage(7403)`,結果 **segfault**。

那不是修正有問題,是**測試無效** —— `setImage()` 的完整流程要在 VGA 子系統備妥之後才能呼叫。更值得注意的是:同一批測試裡,前面幾項(`setImage(99)`、`setImage(65000)`)之所以「通過」,是因為它們都走防護的提早返回,**根本沒進到函式本體**。也就是說那幾項驗到的只是防護本身,不是防護之後的路徑。

改成「只驗上界判定 + 單獨呼叫 `loadZone(74)`」之後才拿到乾淨的結果。

> 用合成呼叫驗證防護時,要確認自己驗到的是哪一條路徑。全部通過但其實每一項都在同一個提早返回上打轉,是很容易發生的假驗證。

## 結論

1. `setImage()` / `animate()` 對 `_vgaBufferPointers` 的索引沒有上界檢查,而圖號的型別容許 zone 達到 655,陣列只有 450 項。
2. 越界的位置落在 `AGOSEngine` 物件內部,不會當場崩潰,而是讓後續流程拿到垃圾指標,在無關的位置倒下。
3. 這一類越界 ASan 抓不到,五輪掃描在發現它之前全部乾淨。
4. Elvira 1 的實際 zone 上限是 74(靜態盤點與檔案清單一致),82 是加上 10% 邊際後的值。
5. 加大陣列無法解決:哨兵值 `0xFFFF` 靠尺寸永遠追不上,而垃圾值的入口只有兩處。
6. 修正後合法的 zone 74 仍正常載入,200 次操作誤擋 0 次。

## 建議

1. 這道上界檢查與缺檔防護一併保留在本專案的 patch 內。
2. 其他 AGOS 遊戲要沿用時,`kChtElvira1ZoneLimit` 那個數字必須**重新量**,不要照抄 —— 每款遊戲的 zone 上限不同。量法見〈上界怎麼訂〉。
3. 涉及記憶體安全的改動,ASan 掃描之外要另外做一次「陣列索引來源」的靜態盤點。這顆的發現方式就是後者。

## 有效性威脅

**內部效度。** 「這顆會造成隨機當機」是從機制推導出來的(越界讀 → 垃圾指標 → 遠端崩潰),**沒有實際觀測到一次由它引發的崩潰**。修正之後也無法用「不再當機」反證,因為原本就重現不出來。這是本篇最弱的一環,已列入開放項目。

**外部效度。** 只在 Floppy/DOS/English 的 64 位元 Linux 建置上驗過。32 位元平台的位移不同(每項 24 bytes),macOS / Windows 上未做等價量測 —— 不過修法與平台無關,風險主要在「越界後讀到什麼」這一段的描述,不在修法本身。

**建構效度。** 「誤擋 0 次」量的是防護的警告次數,證明的是正常路徑沒被擋;它不證明所有畫面元素都正確顯示。判定畫面正常用的是人工看截圖,不是像素比對。另外,220 次操作只走到 zone 69,並沒有實際觸及 74 —— zone 74 能載入是靠單獨呼叫 `loadZone(74)` 驗的,不是遊玩中自然走到的。

**結論效度。** 靜態盤點的最大值建立在「dump 涵蓋了全部腳本」這個前提上,依據是補上 `loadTablesIntoMem()` 迴圈後 dump 從 13 萬行增加到 17 萬行。沒有做「再多載一輪還會不會變多」的收斂測試,所以不能排除仍有分頁沒進來、而其中有更大的圖號。若真有,10% 的邊際可能不夠。
