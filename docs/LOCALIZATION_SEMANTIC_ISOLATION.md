# 中文化的顯示與語意隔離

翻譯只能改變玩家看到的內容，不應改變條件判斷、資源查找、存檔名稱、腳本鍵值、
序列化資料或網路協定。若一個共用字串函式同時服務這兩類用途，必須在 API 上明確
分流，不能假設所有呼叫者都在顯示文字。

## 已證實案例

Elvira 1 的 `oe1_isCalled()` 透過 `getStringPtrByID()` 比較敵人名稱。原始英文
`The soldier` 與 `the soldier` 在不分大小寫比較下相等；譯文「那名士兵」與
「士兵」不相等。全域翻譯掛勾因此讓敵人分類條件失敗，戰鬥圖片變數保持 0，
下游誤載不存在的 `002.VGA`。玩家提供的 v1.2.4 繁中／英文 log、相同核心資料
雜湊與原始碼呼叫鏈共同證實這條因果關係。

## 實作原則

1. 原始字串取得與顯示本地化是兩個責任。API 應提供明確 gate，或乾脆拆成兩個函式。
2. 顯示路徑可以預設本地化；比較、查找、序列化與識別用途必須明確要求原始資料。
3. 不要靠統一幾條譯文修測例。那會讓程式契約依賴翻譯內容，新增語言或改文案就會再壞。
4. 盤點掛勾的所有呼叫者，不能只檢查最先出錯的一個函式。

## 驗收

- 用相同資料與操作做原文／譯文差分，確認差異只出現在顯示。
- 找出原文規則相等、譯文合理但不相等的案例，證明語意路徑仍以原文判斷。
- 覆蓋條件比較、資源名稱、存讀檔、腳本鍵值與序列化呼叫點。
- 走真實玩家路徑，確認修正後能完成受影響流程；單純啟動與畫面截圖不算充分驗證。

## 審查問題

- 這個字串會被畫到螢幕，還是會被程式拿來做決策？
- 翻譯改變大小寫、冠詞、量詞、標點、正規化或字元編碼後，判斷是否仍成立？
- 若新增第二種語言，是否需要翻譯人員知道隱藏的程式規則？若需要，責任邊界就放錯了。
